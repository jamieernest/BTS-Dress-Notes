## Authentication

Every page (`/`, `/config.html`, `/overlay.html`, `/overlay-cast.html`, `/recall.html`, and all of `express.static`) sits behind a Keycloak OIDC login (`server.js`, guard registered before `express.static`), except overlay requests from loopback (below). `/login`, `/callback`, `/logout` and `/logged-out` (plus `base.css` and the favicon it uses) are the only unauthenticated routes. The server will not start without `SESSION_SECRET`; it starts without `KEYCLOAK_ISSUER`/`KEYCLOAK_CLIENT_ID`/`KEYCLOAK_CLIENT_SECRET` but every page then 503s at `/login` until they're set and the process is restarted (Keycloak discovery only runs once, at boot). One shared Keycloak client is used across every venue, unlike the per-venue `EOS_HOST`/`EOS_PORT` vars.

`note.userId`/`comment.userId` are the Keycloak `sub` claim (stable per account), not `socket.id` — this is what makes identity survive a page refresh or reconnect. Only that `userId` may edit a note (`canEditNote()` in `public/note-author.js`, enforced in `server.js`); a note with no `userId` is ownerless and editable by anyone, but `note-delete` needs a matching `userId`, so ownerless notes can't be deleted. Replies (`comment-delete`) follow the same author rule. Backups and exports carry an `authors` list; `applyAuthors()` (`notes-backup.js`) drops any `userId` not in it (legacy socket ids) on restore and import. The Socket.IO handshake is authenticated via `io.engine.use(sessionMiddleware)` + an `io.use(...)` guard that reads `socket.request.session.user`; there is no separate per-socket login.

Sessions persist across restarts in git-ignored `local-sessions.json` via the in-repo `session-store.js` (no external session service, by design). The login is rolling (`SESSION_IDLE_MS`, 12 h idle) but a socket makes no HTTP requests, so every page loads `public/keepalive.js`, which hits `GET /session` every 5 min (a 401 there means the login is gone). The cookie name carries the port (`bts-notes.sid.<PORT>`) so instances on one host don't clobber each other. An in-flight login lives in the server's `pendingLogins` map keyed by OIDC `state`, not in the session, so parallel logins from several tabs can't overwrite each other; each also sets a per-state `bts-notes.login.<PORT>.<state>` cookie that `/callback` must present, so a callback URL started in another browser can't log this one in; `returnTo` travels in the `/login` query (same-site paths only, `safeReturnTo()`). `requireAuth` redirects HTML GETs and 401s everything else. `/logout` emits `logged-out` to that session's sockets and ends at `/logged-out` (through Keycloak's end-session, whose `post_logout_redirect_uri` it is), never `/login`: Keycloak's own login outlives ours and would sign the person straight back in. Pages send a `logged-out` socket event to `loggedOutUrl()`, but the tab that sent the logout form ignores it, since leaving would cut its redirect through Keycloak short.

`loopback-overlay.js` is that exemption: only the overlay pages, their assets, `/session?overlay=1` (the keepalive ping) and an `overlay` socket, and only when `req.socket.remoteAddress` is loopback with no `X-Forwarded-For`/`Forwarded`/`X-Real-IP` header (so a same-host reverse proxy can't make remote clients look local). Such a socket gets a synthetic `local-overlay` user and stays read-only.

Pages identify themselves with `io({ auth: { page } })` (`main`, `config`, `overlay`; `pageOf()` falls back to the Referer). The online users list is one entry per person (`sub`), not per tab; `user-joined`/`user-left` fire for their first and last page. The main page disconnects on `pagehide` so a page in the back/forward cache isn't counted.

All client input goes through `note-input.js` before it touches `globalState`; handlers are wrapped so a bad message can't crash the server. Comments, like notes, can only be changed by their author.

The main page keeps a submitted note as pending until the `note-submit` ack arrives; its pending row appears only after 800 ms while connected (immediately offline), so quick sends draw once in their final scene group. It resends every unacknowledged note on each connect; the server dedupes resends by the note's `clientId` together with its `userId` (`public/index.js` pending-notes section). Pending notes are also saved per `sub` in localStorage (`public/pending-notes.js`, shared by all that person's tabs, so change it one entry at a time with `add`/`remove`, never rewrite the list) and resent on the next load; an ack with `{ error }` means refused, don't resend. The half-written note and its frozen timecode are kept in sessionStorage (`note-draft`), so a bounce through `/login` keeps it.

`openid-client` is on v6, which is ESM-only and has a very different functional API from v4/v5 (`discovery()`, `buildAuthorizationUrl()`, `authorizationCodeGrant()`, etc. — no more `Issuer`/`Client` classes). `server.js` is CommonJS, so it's loaded via a dynamic `import('openid-client')` inside the async `initKeycloak()` startup function rather than `require()`. It also refuses non-HTTPS issuers by default; `initKeycloak()` passes `{ execute: [oidc.allowInsecureRequests] }` to `discovery()` automatically when `KEYCLOAK_ISSUER` starts with `http://`, since a venue-LAN Keycloak instance may not have TLS.

A note resent after an outage carries `ageMs` (recomputed per send); the server stamps `timestamp` as its clock minus that age and inserts by stamp (`public/note-order.js`), so list order is write order, not arrival order. Browsers show it newest first by default; the notes page toolbar toggle switches to oldest first (`notes-order` in localStorage, `orderedGroups()` in `public/index.js`; pending rows stay at the newest end, scene headers stick below the toolbar). The server's array, backups and the JSON export stay oldest first. The browser's frozen timecode, scene (`act`) and LX cue are kept; missing or invalid scene/cue values fall back to the server's current values at arrival.

## Untrusted input and XSS

Everything from a socket goes through the zod schemas in `note-input.js` / `chat-restore.js` before it is stored; an imported or restored backup is rebuilt with `cleanStoredNotes()`/`cleanStoredTags()`, never stored as sent. In the browser, never assign `innerHTML`: use `SafeHtml.setHtml()` (DOMPurify, served from node_modules at `/vendor/purify.min.js`) with every value passed through `escapeHtml()` and every colour through `safeColour()`, or set `textContent` (`public/safe-html.js`). helmet sends a CSP with `script-src 'self'`, so no inline `<script>` or `on*=` attributes in any page (keep JS in `.js` files; `test/security-e2e.test.js` checks); HSTS and upgrade-insecure-requests are off because venues serve plain HTTP. Sockets from another site's Origin are refused (`sameOrigin()`), and logout is a `POST /logout` form so a link elsewhere cannot sign people out. `qs` is pinned through `overrides` in `package.json` because Express 4 holds it to a vulnerable 6.14.

Profile photos reuse the BTS website’s `/images/profiles/<username>.jpg` (500×500 JPEG). `profile-photos.js` validates only `preferred_username` from OIDC with Zod (any email domain); missing/invalid usernames retain initials, never guess from email. The historical `emailPrefix` wire field now holds only that username, never full email. Shared URL rules live in `public/profile-photos.js`; Helmet allows only the fixed website image origin, and `SafeHtml.setHtml()` binds photo-error fallback after DOMPurify. Existing sessions without a photo username need a fresh login. See README for the source audit.

## Frontend HTML and icons

The CSP (helmet in `server.js`) allows only `'self'` scripts, so no inline handlers or `<script>` blocks. Build markup through `SafeHtml.setHtml` (DOMPurify, `public/safe-html.js`), never `innerHTML`. Icons are symbols in `public/icons.svg` (`<use href="icons.svg#i-name"/>` in source HTML). The authenticated HTML routes in `server.js` include that shared sprite and switch uses to local ids, so icons paint with the page; keep it as the single source. DOMPurify's html profile strips `<svg><use>`, so templates emit `<i data-icon="name">` placeholders that `NoteView.setHtml()` swaps for the sprite.

Author filtering uses `filters.author` = exact Keycloak `note.userId` (empty means anyone), composed with `search`, `act` and `tag`. `NoteView.createAuthorSearch()` derives offline authors from notes, never names as identity; Past notes accepts account ids only from the export’s `authors` manifest, leaving legacy/ownerless notes searchable as text. Both notes pages keep filters in `scene`, `tag`, `author`, `mentioned`, `q` URL parameters. People suggestions distinguish “By” (author) from “Mentions” (`filters.mentionedUserId`, including note replies), with independent removable chips.
Notes and their comments carry bounded `agreements: [{ userId, name, emailPrefix? }]` keyed by Keycloak sub (`note-agreements.js`; `emailPrefix` is the profile-photo username, so the list can show photos); `note-agreement-toggle` and `comment-agreement-toggle` derive the actor from the session and broadcast a small `agreements-update` delta ({ noteId, commentId?, agreements }), not the notes list. Imported/restored lists are cleaned in `note-input.js`; missing lists are valid. `NoteView.agreementsHTML()` is read-only unless passed an actor. Its fixed thumb/count slots show people on hover/focus or count click (including zero); the top-layer popover escapes clipped note corners. The notes page applies that delta with `NoteView.updateAgreements()` in place (a full `notes-update` that differs only in agreements does the same), preserving row/action nodes and focus rather than restarting their hover transitions.

Shared UI lives in `public/note-view.js` (note, reply, tag chip, avatar and scene-group templates; search/filter matching; the colourful filter dropdown `createDropdown()`) and `public/timecode-format.js` (every timecode and time-of-day display). The notes page and Past notes both draw through them; extend these rather than re-implementing a variant in a page script (`test/note-view.test.js`). Scene grouping uses `NoteView.groupNotes()` on the full newest-first list: one heading per visit to a scene (a scene that returns after others gets a new group at the current end, not merged into its earlier one), ordered by earliest captured `startedAt` (legacy fallback: `timestamp`), so cross-scene submissions stay with their scene on both pages. Heads on the notes page are matched to groups by position, not scene name. Filter after grouping to preserve scene order. Scene headings are buttons: on the notes page they scroll to the visit's earliest row (`NoteView.visitStartRow()`, honours the order toggle); in the playback sidebar they seek to `PlaybackTimeline.visitStart()`. Both go by the heading's own visit, never by label.

Note headers show person, cue and global reference; exact note timing stays in data/playback. Scene headers use `NoteView.groupStartTimes()`: a scene's first group takes `NoteView.sceneStartTimes()` (first valid scene-log entry per name, else oldest retained note timestamp from the full list), a returning group its own earliest note time; both use shared `TimecodeFormat.formatClockMinute()` for HH:mm in the viewer’s timezone. Filtering must not recompute that start from visible notes.

`public/base.css` (tokens, buttons, topbar, chips, selects) is loaded by every page; each page's own CSS only adds its layout. A note always keeps at least one tag: the composer requires one (and starts each note with the tags that person last selected, including an empty selection, `last-tags:<sub>` in localStorage via `public/composer-tags.js`; drafts never override it), the tag picker (opened from the note's tag chips) won't untick the last, and the server's `note-update-tags` refuses an empty list. Keep backend detail (saving, servers, sockets) out of user-facing text.

Button and menu labels use plain action text without trailing ellipses. Shared popover positioning and resize handling live in `public/note-view.js`: mobile keyboard height changes keep menus inside the visual viewport; width changes dismiss them. Scene/tag dropdowns follow their sticky toolbar anchors on scroll on both notes pages. `NoteView.watchNavigation()` measures the topbar and connection banner for the toolbar offset; the composer scrolls with the page.

Phone composition (`public/index-style.css`, `public/index.js`) shows tag choices above a separate Discard/Send row and keeps the composer in the page's scroll flow. Enter adds a line with a coarse pointer (touch devices); desktop Enter submits at every window width, Shift+Enter adds a line (`typeToNote.shouldSubmit()`, shared by notes, chat, replies and edits). Chat fills the screen below 860px; its height and offset follow `visualViewport` so the keyboard does not cover Send, and the underlying page is inert. Chat scroll anchoring lives in `public/chat-scroll.js`: keep its pre-layout state, and render messages inside `chatMessageContent` so its ResizeObserver sees late content growth as well as composer/viewport changes. Chat is labelled "Shitposts" in the UI. On wide screens it starts open unless the person last closed it there (`shitposts-open` in localStorage, `index-boot.js`); narrow screens always start closed and don't save the choice.

The main page draws this tab's last notes and header state (`public/notes-snapshot.js`, sessionStorage, saved on `pagehide`/hidden, cleared on logout) before the socket connects; server updates always replace them. `public/index-boot.js` restores the chat layout before paint. `public/loading-state.js` shares delayed skeletons and their minimum visible time across notes, chat and saved shows; cached content bypasses the delay. Keep the initial loading classes in HTML so neither defaults nor empty states flash before scripts run. `rebuildFullNotesList()` draws progressively (first 30, then batches via `setTimeout`), so code that needs every row drawn can't assume it right after a rebuild. `notes-update` with the same ids updates changed notes in place (`updateNoteElement`) rather than rebuilding; avoid adding full rebuilds to connect-time handlers, since each costs about 0.5 ms per note in DOMPurify.

Show tags are managed on `/config.html`; `create-tag` and `delete-tag` acknowledge validation/persistence errors, and tags used by live notes cannot be deleted. Tag writes use temp-file rename before changing live state. `createComposerTags().reconcile()` removes obsolete sticky selections on `tags-update`.

## Eos OSC input

LX cue text arrives two ways, both routed through `handleOscMessage()` in `server.js`: the TCP connection to the desk (`EOS_PORT`, 3037) and the UDP OSC server (`OSC_PORT`). Port 3037 is OSC 1.1 SLIP-framed, and one TCP `data` chunk routinely holds several packets, so never parse raw chunks as strings; decode with `eos-osc.js`. Cue text is `<list>/<label> <time> [<percent>]`, and labels can contain `/` (e.g. `1/1899 B/O 3.0 100%`); during a fade Eos resends it with a falling time and rising percentage. `npm test` runs regression tests built from captured desk traffic. Set `DEBUG_EOS=1` to log every decoded TCP message.

The Eos TCP socket is owned by `connectToEOS()` in `server.js`: opened at start and by the config page's "Reconnect to Eos" button (`eos-reconnect`), never retried automatically. State (`connecting`/`connected`/`failed`/`disconnected`) goes to every client as `eos-status`; a press while `connecting` is ignored, otherwise the old socket is destroyed first so only one is ever live. `test/eos-reconnect-e2e.test.js` uses a stand-in TCP console.

## Type to start a note

`public/type-to-note.js` decides (unit-tested in `test/type-to-note.test.js`) when a keydown anywhere on `/` focuses `noteInput`; focus is what runs `startTyping`, and the browser delivers that same keystroke to the box, so don't `preventDefault` or insert the character yourself. Escape in the note box is `escapeAction()` in the same file: it cancels and blurs only an empty box; a written note keeps focus, text, tags and its frozen stamp so Enter still sends it. Desktop Enter can also send a restored/blurred draft when only BODY is focused and no popover or modal is open (`shouldSubmitDraft()`). `leaveAction()` cancels when focus leaves the composer for elsewhere on the page with the box empty. Once the box has been empty for `EMPTY_RELEASE_MS` (5 s, restarted by focus, input and blur), `emptyBoxAction()` unfreezes the timecode (still focused; the next key freezes it again) or cancels the note (box left).

## Timecode sources

`globalState.timeMode` is `midi`, `network` or `realtime`. MIDI and network timecode each have their own `createMtcDecoder()` (`mtc.js`) and state (`globalState.timecode` / `globalState.networkTimecode`); every `timecode-update` carries `source`, and clients display only the source matching the mode. Network timecode is the ETC Response MIDI gateway's ACN/SDT multicast (UDP 5568, shared with sACN), parsed by `acn-midi.js`; see the README for settings. The venue switch does IGMP snooping, so nothing arrives without a group join, and on Wi-Fi every packet arrived twice (hence the SDT sequence filter). `npm test` covers it with packets captured from the gateway.

The MIDI input and multicast interface are chosen on `/config.html` and saved to git-ignored `local-settings.json`, which beats `GATEWAY_IFACE` (env vars are only first-run defaults). With neither set, `gateway-lock.js` joins the group on every interface and locks onto the first gateway heard (dgram doesn't report the arrival interface, so it's the joined interface on the gateway's subnet), releasing after `NETWORK_LOST_MS` of silence. `config.html` sockets are left out of the online users list (`listedUsers()`) but can still change settings, unlike overlays.

## Chat restore

Desktop chat width is shared by drawer/page layout through `--chat-width`; `public/chat-resize.js` owns divider pointer/keyboard controls and the `shitposts-width` preference. `index-boot.js` applies it before paint. Viewport clamps preserve the preferred width; below 861px the divider is hidden and chat remains full-screen. Keep `chatScroll.layoutChanged()` on live width changes.

Chat lives only in `globalState.chatMessages`, with no length cap; the hard ceilings are the browser's ~5 MB localStorage and the socket's `maxHttpBufferSize` (16 MB, `server.js`), and `public/chat-copy.js` cuts to the most recent messages when either is hit. New messages go out alone as `chat-message-added`; the full list (`chat-messages-update`) is only sent on connect and after a restore.

Shitposts replies store only optional `replyTo` (a message id); `public/chat-replies.js` shares id validation and flat quote context, while `index.js` resolves targets through its message map. Missing targets are allowed (restart or cache trimming) and render as unavailable. `chat-restore.js` includes `replyTo` in vouch equality and rejects malformed/self references; never drop reply metadata from browser copies. Chat remains outside notes backups/exports and Past notes.

After a restart clients offer their copy (`chat-restore-offer`). `chat-restore.js` restores the fullest log that two distinct users vouch for (a log vouches for another that contains all its messages, same id and content), merging it into the messages already on the server by timestamp and id, so messages sent after the restart don't block it and a later, larger agreed log still adds to it. The window opens at start and closes `CHAT_RESTORE_WINDOW_MS` later (default 30 min); the server tells clients via `chat-restore-status` (sent before the log on connect). While it is open a browser only grows its copy; once closed it adopts the server's log.

The copy is kept in `localStorage` (2 h expiry), not page memory, so it survives reloads and `/login` bounces while the server is down. `test/chat-restore-e2e.test.js` runs the real `server.js` against a stub OIDC provider (`SESSIONS_FILE` overrides the session file) with logged-in users through restarts, reloads and a lost session.

## Notes backup, restore and reset

Human note references use `note.noteNumber`; UUID `id` remains authoritative. `public/note-numbers.js` handles legacy oldest-first migration and reset-merge collisions; `nextNoteNumber` travels in backups/exports/saved shows, including when no notes remain, so deletions never release numbers. Only a show reset starts at 1. New notes allocate on server acceptance (offline arrivals keep their older timestamp without renumbering existing references); deduped resends keep their number, pending rows have none. Reset merges preserve live references and reassign incoming numbers below the live high-watermark. Past notes/playback migrate legacy files locally.

Notes live only in `globalState.notes`; `server.js` `backup()` writes them (with tags) to `backups/` through a temp file and rename (`notes-backup.js`): `scheduleBackup()` about `BACKUP_DELAY_MS` after every change (a newer file from the same minute replaces the last, so roughly one per minute), every minute as a safety net, and on crash/SIGINT/SIGTERM. On start `restoreNotes()` loads the newest backup under 2 hours old that passes `checkBackup()`, falling back to older ones; `backup()` refuses to run until that has happened so an empty server cannot outrank a good backup. Age and order come from the timestamp in the file name, not mtime. Restored tags stay in memory only (`tags.json` is a tracked file). The "Reset all notes and chat" button on `/config.html` sends `reset-all` (same non-overlay rule as the other settings); `resetNotesAndChat()` clears both, closes the chat restore window, tells browsers (`all-reset`: drop chat copy and unsent notes) and writes a backup at once so a restart stays empty. Tags return to the six definitions in `default-tags.json` (never use mutable `tags.json` as defaults); writing those defaults must succeed before clearing live state. Before clearing, every reset (including Save and reset) writes the notes to git-ignored `reset-notes/` (`reset-notes.js`, `RESETS_DIR`); if that write fails nothing is reset. They are kept for 3 days (`RESET_KEEP_MS`) and pruned by file-name time, with no delete in the UI. The config page lists them (`resets-list`, `resets-update`), and `restore-reset` merges them back in by note id, restoring needed tag definitions (remapping conflicting ids to preserve both meanings), so restoring twice adds nothing. Chat and videos aren't kept. `BACKUPS_DIR`, `BACKUP_INTERVAL_MS` and `TAGS_FILE` exist for the tests (`test/e2e-harness.js` is shared by the e2e tests).

Saved shows (`saved-shows.js`) are named copies of the notes export in git-ignored `saved-shows/` (`SAVED_SHOWS_DIR`), one file per show, id = file name. The config page's "Save notes" sends `save-show` (`{ name, reset }`, acked; reset runs only after the file is written). They are never loaded back into live notes or aged out. Past notes lists them from `GET /shows` and opens `GET /shows/:id` (ids are checked against a pattern, never joined as paths); an open show and its filters live in the URL (`?show=&scene=&tag=&q=`) so a reload keeps them, while a file opened from the computer stays client-side only. Chat is not saved.

## Show log and video playback

`globalState.showLog` records scene/LX changes with wall-clock times (`show-log.js`, dropping fade-progress repeats), travels with `notesExport()` through backups and saved shows, and broadcasts as `show-log-update`. Notes carry `startedAt`, worked out from `startedAgeMs`. Playback timing lives in `public/playback-timeline.js`; older exports infer scenes from notes and omit cue marks.

`public/playback-context.js` builds live/saved/local-file links and safe return paths. `/playback.html?source=live` loads authenticated, uncached `GET /playback/live` and refreshes on note changes; `?show=` reads `/shows/:id`; `?file=` reads this tab's sessionStorage. `?note=` waits for video metadata/timing before seeking three seconds before the note. Return links preserve saved-show filters and highlight the note. Local file keys use `getRandomValues`, since `randomUUID` is unavailable on HTTP venue/Tailscale pages.

A recording is one or more parts, laid on one timeline by start time with gaps between them (`public/playback-program.js`; the player swaps the `<video>` source per part and runs a clock through gaps). Uploaded parts (`recordings.js`, `/recordings/:collection` in `server.js`) live in `RECORDINGS_DIR/<collection>/` with a `recordings.json` index; the collection is `live` or a saved-show id. Uploads stream raw to disk (`RECORDING_MAX_BYTES`, `requestTimeout` raised to 6 h) and changes broadcast as `recordings-update`. `save-show` copies the live collection before any reset; reset removes it. Live and saved-show playback use shared uploads; locally loaded notes (`?file=`, excluding the built-in sample) can use device-only blob videos; `/config.html?recording=<collection>#recordings` selects the upload target.

`npm run dev:playback` starts the sample instance on 3030 (`PLAYBACK_PORT` overrides), using `.env` login settings and separate git-ignored `.playback-dev/` notes, tags, backups and saved shows. `PLAYBACK_DEMO=1` seeds invented live notes only when empty and adds a sample saved show without overwriting existing ones. `/playback.html?demo=1` remains a standalone sample; assets live in `public/playback-demo/` (`scene.svg` is the recording's source).

## Mentions

`public/mentions.js` owns the shared picker, validation, escaped rendering and edit-range rebasing. Optional `mentions` on notes, note comments and chat messages is at most 20 `{ userId, name, start, end }` entries: `userId` is OIDC sub, `name` is a snapshot (both at most 200 characters), and `[start,end)` is a non-overlapping UTF-16 range whose text is exactly `@` + name. Plain typed names never imply identity. Suggestions use existing authors and online accounts only. `note-input.js` and `chat-restore.js` clean metadata; chat agreement includes it. `NoteView.noteMatches` accepts `filters.mentionedUserId` (matches note or its comments); navigation can set this independently of author filters. The Shitposts mention badge uses per-account localStorage seen message IDs, clears on viewing, and ignores self mentions; notes have no notification badge.

Scene labels (the OSC `/bts/` act text) can mention people too: `Mentions.labelHtml()` highlights `@username` (the profile-photo username, `emailPrefix` on the wire) at draw time only, for known accounts; the stored label is unchanged and has no `mentions` metadata. Anything that draws a scene label must pass the current account list, and the main page redraws group headings when it changes (`refreshGroupLabels()`). The "My scenes" scene filter (`NoteView.MY_SCENES`, listed under "All scenes") keeps only scenes whose label mentions the viewer's username, using the same token rule as the highlight (`Mentions.labelMentions()`); it is stored in the `scene` URL parameter as `@my-scenes`, and `noteMatches()`/`sceneOptions()` need the viewer's username passed in.
